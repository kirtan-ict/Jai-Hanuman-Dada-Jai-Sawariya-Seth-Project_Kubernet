EKS vs AKS vs GKE: choosing a managed Kubernetes service

All three hyperscalers run conformant Kubernetes. The differences that matter show up in networking, identity, node lifecycle and day-two operations, and in how well each one fits the organisation you already have.

  • Architecture
  • 9 min read
  • By KubeSetu Engineering

Teams often approach this decision as a feature comparison: which service has the newest Kubernetes minor version, which one has the slickest console, which one launched a headline feature last quarter. Those comparisons age badly. Every provider ships changes constantly, and a feature gap today is frequently closed within a release cycle or two.

A more durable way to choose is to look at the architectural seams where a managed service makes decisions on your behalf, and ask whether those decisions suit your workloads, your skills and your existing cloud estate. This article walks through those seams and finishes with a short decision framework.

A note on versions and pricing. Supported Kubernetes versions, support windows, control plane fees and feature availability change regularly and can differ by region. Treat anything you read here as a map of the terrain, then check the official release notes and pricing pages for each provider before you commit.

What "managed" actually covers

In all three services the provider runs the control plane: the API server, etcd, the scheduler and the controller manager. You do not patch those machines, back up etcd yourself or size the API server. You do still own most of what makes a cluster useful:

  • Worker node configuration, operating system choice and upgrade cadence (unless you opt into a fully managed node mode).
  • Cluster add-ons such as ingress controllers, DNS tuning, certificate management, policy engines and observability agents.
  • Workload security: RBAC, Pod Security, network policy, secrets handling and image provenance.
  • Capacity planning, autoscaling configuration and cost governance.

The line between "provider" and "you" is drawn slightly differently by each service, and each now offers a more opinionated mode that pushes the line further toward the provider. GKE Autopilot, EKS Auto Mode and AKS Automatic all manage nodes, scaling and a curated set of add-ons for you, at the cost of some flexibility. If your team is small and your workloads are conventional stateless services, those modes deserve serious consideration before you reach for the standard tier.

Control plane and upgrades

Each provider publishes a support calendar for Kubernetes minor versions and eventually upgrades clusters that fall out of support. The questions to ask are:

  • How much control do you get over timing? Look for maintenance windows, exclusion periods and release channels. GKE and AKS both offer channel-based automatic upgrades; EKS leans toward explicit, operator-driven upgrades, with an extended support option for older versions.
  • What happens to nodes? Control plane upgrades are handled by the provider, but node pools usually follow separately. Find out whether node upgrades are automatic, how surge is configured, and how the service respects PodDisruptionBudgets during a drain.
  • Is there an uptime commitment? Providers typically offer a financially backed SLA only on certain tiers. Read the current terms rather than assuming.

Whichever service you choose, build an upgrade routine you can run every few months. Our upgrade playbook covers that process in detail.

Networking models

Networking is where the three services differ most, and it is the hardest thing to change after the fact.

ConcernAmazon EKSAzure AKSGoogle GKE
Default pod networkingVPC CNI: pods get routable VPC IP addressesAzure CNI, with an overlay option that conserves VNet address spaceVPC-native: pods use alias IP ranges in the VPC
IP planning pressureHigh with flat VPC IPs; prefix delegation and custom networking helpLower with overlay mode; higher with flat VNet IPsModerate; secondary ranges must be sized up front
eBPF dataplane optionBring your own (for example Cilium)Azure CNI powered by CiliumGKE Dataplane V2 (Cilium-based)
Network policySupported through the VPC CNI or a third-party engineAzure, Cilium or Calico enginesBuilt into Dataplane V2

The practical lesson: plan your address space before you create the first cluster. Flat, routable pod IPs make integration with existing VPC or VNet resources simple, but they consume addresses quickly. Overlay models save addresses but add a translation hop when pods talk to things outside the cluster. Neither is wrong; picking one by accident is.

Identity and access

Every serious workload eventually needs to call a cloud API: read from object storage, pull a secret, publish to a queue. The secure pattern on all three clouds is the same in principle. A Kubernetes ServiceAccount is federated to a cloud identity, and pods receive short-lived credentials automatically, with no static keys stored in the cluster.

The wiring differs. On EKS you can use IAM Roles for Service Accounts (IRSA) or the newer EKS Pod Identity. AKS uses Microsoft Entra Workload ID. GKE uses Workload Identity Federation for GKE. Here is what the ServiceAccount side looks like on each:

# Amazon EKS (IRSA): annotate with the IAM role ARN
apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-api
  namespace: orders
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::111122223333:role/orders-api
---
# Azure AKS (Workload ID): annotate with the managed identity client ID
# Pods must also carry the label azure.workload.identity/use: "true"
apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-api
  namespace: orders
  annotations:
    azure.workload.identity/client-id: 00000000-0000-0000-0000-000000000000
---
# Google GKE (Workload Identity): annotate with the Google service account
apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-api
  namespace: orders
  annotations:
    iam.gke.io/gcp-service-account: orders-api@my-project.iam.gserviceaccount.com

Human access matters just as much. EKS maps cloud principals to Kubernetes permissions through access entries; AKS integrates with Entra ID and can use Azure RBAC for Kubernetes authorisation; GKE integrates with Google Cloud IAM and Google Groups for RBAC. If your organisation already has a mature identity platform in one cloud, that alone can tip the decision.

Avoid static cloud keys in Secrets. Long-lived access keys stored as Kubernetes Secrets are one of the most common findings in cluster reviews. Workload identity federation exists on all three platforms; use it from day one.

Nodes, autoscaling and compute choice

All three services support managed node groups or pools with a choice of instance families, including Arm-based and GPU instances. The meaningful differences are in how capacity is added and removed:

  • EKS works with the Kubernetes Cluster Autoscaler and with Karpenter, which provisions individual right-sized nodes directly from pending pod requirements rather than scaling predefined groups. EKS Auto Mode builds on that approach as a managed feature.
  • AKS ships a managed Cluster Autoscaler per node pool and offers node auto-provisioning based on Karpenter.
  • GKE offers a managed Cluster Autoscaler with node auto-provisioning, and Autopilot removes node management entirely by billing for pod resource requests.

If you run bursty or heterogeneous workloads, flexible provisioning and spot or preemptible capacity can make a large difference to your bill. Our cost optimisation guide covers those trade-offs. Before you commit, check that the instance types you need, especially GPUs, are available in your target regions with the quota you expect.

Day-two operations and ecosystem

The provider console is rarely where your team will live. Instead, look at how each service fits your operational tooling:

  • Observability: each cloud has native integrations (CloudWatch Container Insights, Azure Monitor, Google Cloud Observability) and managed Prometheus offerings. If you already run a vendor-neutral stack, confirm that agents and exporters are supported on the node images you plan to use.
  • Add-on management: EKS add-ons, AKS extensions and GKE managed components handle CSI drivers, CNI and DNS. Know which ones the provider upgrades for you and which ones you must version-pin yourself.
  • Infrastructure as code: all three are well supported by Terraform, OpenTofu, Pulumi and Crossplane. Provider-specific CLIs (eksctl, az aks, gcloud container) are handy for experiments but should not be your source of truth.
  • Hybrid reach: EKS Anywhere, Azure Arc and GKE's attached and on-premises options extend each ecosystem beyond the public cloud. If you also run clusters on premises or at the edge, evaluate how consistent the experience really is.

A quick sanity check that works identically on any of the three:

# Confirm which API server and node versions you are actually running
kubectl version
kubectl get nodes -o wide

# See which add-ons and system components are installed
kubectl get pods -n kube-system -o wide

# List the API groups the cluster serves (useful when comparing providers)
kubectl api-versions | sort

Understanding the cost model

The control plane fee is usually the smallest line item. The real cost drivers are compute, storage, load balancers, NAT and cross-zone or egress traffic, logging ingestion and support plans. When comparing providers:

  • Model your workload at realistic utilisation rather than comparing list prices for identical instance sizes.
  • Include data transfer. Chatty microservices spread across zones can generate surprising inter-zone charges on any cloud.
  • Account for committed-use discounts, savings plans or reservations you already hold. Existing commitments often make one provider clearly cheaper for you specifically.
  • Price the "fully managed" modes on their own terms. Billing per pod request can be cheaper for small or spiky clusters and more expensive for well-packed steady ones.

A decision framework

In our experience, the right answer is usually determined by a handful of organisational facts rather than by technical features. Work through these in order:

  1. Where does your data and identity already live? If most of your estate, data gravity and identity governance sit in one cloud, start there. Crossing clouds for Kubernetes alone rarely pays back.
  2. What does your team already know? Familiarity with one provider's IAM and networking model shortens every incident.
  3. How opinionated do you want the platform to be? If you want minimal node management, compare the fully managed modes side by side. If you need custom kernels, specialised hardware or deep networking control, the standard tiers are a better fit.
  4. What are your regulatory and regional constraints? Check region availability, sovereignty options and compliance attestations for the specific services you will use.
  5. How portable must you be? Keep workloads portable by sticking to upstream APIs, using GitOps, and isolating cloud-specific integrations behind clearly owned components.

If you are weighing managed Kubernetes against enterprise platforms or self-managed clusters, our platform decision guide walks through a broader comparison.

Key takeaways

  • All three services run conformant Kubernetes; the meaningful differences are in networking, identity, node lifecycle and operations.
  • Plan IP address space and choose a CNI model deliberately before you create your first production cluster.
  • Use workload identity federation on every provider instead of static cloud credentials.
  • Evaluate the fully managed modes (Autopilot, Auto Mode, Automatic) if your workloads are conventional and your team is small.
  • Let data gravity, existing identity, team skills and commitments drive the decision more than feature checklists.
  • Verify versions, support windows and pricing against official documentation; they change often.
