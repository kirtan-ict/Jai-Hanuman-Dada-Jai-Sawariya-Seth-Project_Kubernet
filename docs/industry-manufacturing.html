Kubernetes for manufacturing & Industry 4.0

Vision inspection, predictive maintenance and MES integrations all want to run next to the line. We build factory-edge platforms that respect the boundary between operational and corporate networks, keep running when the WAN drops, and can be updated safely from a central team.

Challenges

What makes factory platforms different

OT and IT must stay apart

Control systems cannot be exposed to corporate or internet traffic, yet their data is needed by analytics teams.

Intermittent connectivity

Remote plants may have slow or unreliable links, so local workloads must keep running and catch up later.

Harsh, unattended sites

Industrial PCs and small servers sit on the shop floor with no on-site IT team to fix a failed upgrade.

High-volume sensor data

Machines produce a constant stream of telemetry that must be filtered locally and delivered without loss.

Production windows

Changes must fit planned shutdowns and shift patterns; an unplanned restart can stop a line.

AI at the line

Vision inspection models need GPUs or accelerators close to cameras, managed like any other workload.

Recommended architecture

Edge clusters in an industrial DMZ, synced to a central hub

Following a zoned model in the spirit of IEC 62443 and the Purdue reference model, OT devices stay in their own zone. A small Kubernetes cluster in the plant's industrial DMZ collects and processes data, and only outbound, brokered connections reach the cloud or corporate data centre.

  • Lightweight clusters (K3s, MicroShift or similar) on two or three nodes per plant for resilience.
  • Protocol gateways for OPC UA, Modbus and MQTT that read from OT without opening inbound paths.
  • Local message buffering (for example MQTT brokers or Kafka) so data survives link outages.
  • Pull-based GitOps: plant clusters fetch approved changes, nothing pushes into the plant.
  • Maintenance windows encoded in rollout policies, with automatic rollback on failed health checks.
  • GPU or accelerator nodes for vision inspection, scheduled and updated like other workloads.
Compliance & security controls

From requirement to Kubernetes control

RequirementHow we implement it on Kubernetes
Zones and conduits between OT and IT (as described in IEC 62443)Edge clusters placed in the industrial DMZ, default-deny network policies, read-only protocol gateways, and firewall rules that allow only brokered outbound traffic.
Least-privilege remote access for engineers and vendorsNo inbound SSH or API exposure; access through an audited bastion or zero-trust tunnel with SSO, MFA and time-limited roles.
Secure, controlled software updatesPull-based GitOps, signed images verified at admission, local registry mirrors, and rollouts restricted to approved maintenance windows.
Resilience when connectivity is lostLocal control plane on each plant cluster, store-and-forward queues, and workloads that do not depend on cloud services to keep running.
Information security management (for example ISO 27001)Asset inventory of clusters and devices, documented change records in Git, and central logging of security events.
Device and node integrityImmutable or minimal OS images, disk encryption, secure boot where hardware supports it, and certificate-based node enrolment.
Not legal advice. IEC 62443, ISO 27001 and sector rules are referenced in general terms to explain design choices. Your OT security and compliance owners should confirm the requirements for each site.

FAQ

Manufacturing questions

Will Kubernetes run our PLC or safety logic?
No. Real-time control and safety systems should stay on dedicated controllers. Kubernetes runs the surrounding software: data collection, analytics, vision inspection, dashboards and integrations.
What happens when the plant loses its internet link?
Each plant cluster has its own control plane and local queues, so workloads keep running and data is buffered. Once the link returns, data is forwarded and any pending configuration changes are pulled in.
How small can a factory cluster be?
A single industrial PC can run a lightweight distribution, though we usually recommend two or three nodes so one hardware failure does not stop the site.
