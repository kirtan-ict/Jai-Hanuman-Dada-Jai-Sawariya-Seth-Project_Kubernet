Edge Kubernetes

Hundreds of small clusters, managed like one

Stores, factories, cell sites and vehicles need software close to where data is produced. We build lightweight clusters that keep working when the network drops, and a fleet layer that updates them all safely from one place.

  • k3s
  • k0s
  • MicroK8s
  • KubeEdge
  • Rancher Fleet
  • Argo CD ApplicationSets

When this fits

  • Many locations each need local compute: point-of-sale, video analytics, machine control, network functions.
  • Connectivity is slow, expensive or intermittent, and sites must keep running offline.
  • Latency or bandwidth make sending all data to a central cloud impractical.
  • You want the same deployment model at the edge as in your central clusters.

When it doesn't

  • Each site runs one simple app that rarely changes; a plain container runtime or device-management tool may be enough.
  • Devices are microcontrollers or very small boards that cannot run a container runtime.
  • There are only one or two sites; a regular on-premises cluster is simpler.
  • Nobody owns the central fleet tooling; edge without fleet management becomes unmanageable quickly.
Reference architecture

Pull, cache and keep going

Edge sites cannot rely on a central controller pushing changes. Each site runs a small agent that pulls its desired state from Git when the network is up, caches images locally, and carries on with the last good configuration when it is down.

  • Outbound-only connections from sites, so no inbound firewall rules at hundreds of locations.
  • Groups and waves: target sites by region, hardware or ring, and roll updates out gradually.
  • Local resilience: registry mirrors, buffered telemetry and apps that tolerate a missing cloud.
  • Zero-touch onboarding: a new box is plugged in and registers itself with the fleet.
Implementation

What we implement

  • Distribution selection by footprint and hardware: k3s, k0s, MicroK8s, or KubeEdge when you need cloud-to-device messaging.
  • Single-node and three-node HA site designs, including ARM and x86 hardware.
  • Golden OS images and zero-touch provisioning so a site boots straight into the fleet.
  • Fleet management with Rancher Fleet or Argo CD ApplicationSets, using cluster labels for targeting.
  • Over-the-air update pipelines with canary sites, staged waves and automatic rollback.
  • Local registry mirrors and pre-loaded images for low-bandwidth or offline sites.
  • Lightweight observability: local buffering with OpenTelemetry or Fluent Bit, forwarded when online.
  • Device and sensor integration for retail, manufacturing (OT networks, PLC gateways) and telecom edge sites.

Day-2 operations

Day-2 support we provide

At the edge, operations is mostly fleet operations. Our support plans treat the fleet as the unit of work.

Upgrades

Kubernetes and OS upgrades rolled out in waves, starting with lab and canary sites, with automatic halt when health checks fail.

Patching

Security patches packaged as image updates and delivered over the air, with clear reporting of which sites are still behind.

Monitoring

Fleet-level dashboards: sites online, drift from desired state, last successful sync, disk wear and local resource pressure.

Backup and recovery

Sites are rebuildable from Git and a golden image; local data is synchronised centrally where needed, so a failed box is swapped, not repaired.

Scaling the fleet

Onboarding new sites in batches, managing hardware generations side by side and keeping configuration manageable as site count grows.

Incident response

Remote diagnosis over the management channel, fleet-wide rollback of a bad release, and clear instructions for on-site staff when hardware must be swapped.

Lessons learned

Common pitfalls we prevent

  • Updating every site at once and bricking the fleet with one bad release.
  • Images pulled over the WAN on every restart, saturating thin links.
  • SD cards and consumer disks wearing out under container and log writes.
  • Inbound access to each site instead of outbound, pull-based management.
  • Clock drift and expired certificates on sites that were offline for weeks.
  • Per-site snowflake configuration instead of labels and templates.

FAQ

Edge questions

Related services: GitOps and fleet delivery, observability, platform engineering, and fleet support.

k3s, k0s or MicroK8s?
All three are certified Kubernetes distributions with small footprints. k3s has a large ecosystem and pairs naturally with Rancher. k0s ships as a single binary with very few host dependencies. MicroK8s fits well on Ubuntu with snap-based updates. We choose based on your OS, hardware and fleet tooling.
When do we need KubeEdge?
When the edge nodes are constrained devices that should be managed from a central cluster, or when you need device twins and cloud-to-device messaging. If each site can run its own small cluster, independent clusters with fleet GitOps are usually simpler.
What happens when a site is offline for days?
It keeps running its last applied configuration from local images. When it reconnects, the agent pulls any pending changes and forwards buffered telemetry. We test these scenarios in the pilot phase.
Is single-node Kubernetes acceptable in production?
For many edge sites, yes. The cluster is a disposable unit rebuilt from Git, and the business process tolerates a short outage or has a manual fallback. Where it does not, we use three small nodes.
