Bare-metal Kubernetes

Kubernetes directly on the servers

No hypervisor layer, no licence for it, and full access to every core, NIC and NVMe drive. In exchange, provisioning, networking and hardware failures become part of the platform. We automate all three.

When this fits

  • Performance-sensitive workloads: databases, low-latency services, GPU training, high-throughput networking.
  • Large, steady fleets where hypervisor licences and cloud margins add up.
  • You want to retire a virtualisation layer and run containers and VMs (via KubeVirt) on one platform.
  • You have colocation or data-centre space and remote-hands access.
  • You need predictable, dedicated hardware for compliance or noisy-neighbour reasons.

When it doesn't

  • Small clusters of a few nodes, where losing one server is a big share of capacity.
  • No one can physically replace disks, NICs or servers within your recovery targets.
  • Teams need to create and destroy clusters many times a day (VMs or cloud are faster).
  • Your network team cannot support BGP peering or dedicated VLANs for the cluster.
Reference architecture

Treat servers like cattle, too

The goal is that a server can be wiped and rebuilt from a declaration, just like a cloud VM. A small management cluster holds the desired state; a bare-metal provider talks to each machine's BMC to power it on, boot it over the network and install a known image.

  • Immutable, API-managed OS such as Talos Linux, with no SSH and no configuration drift.
  • BGP instead of appliances: Service IPs and pod routes advertised straight to the switches.
  • Local NVMe for speed, with replication handled by the storage layer or the application.
  • Failure domains mapped to racks and power feeds through topology labels.
Implementation

What we implement

  • Hardware inventory, firmware baselines and BIOS / BMC settings captured as code.
  • Provisioning with Metal3 (Ironic), Tinkerbell, Canonical MAAS or Sidero Omni, driven by Cluster API where it fits.
  • PXE / iPXE boot infrastructure, DHCP and image servers on an isolated provisioning network.
  • Talos Linux, Flatcar or a hardened Ubuntu / RHEL base, chosen to match your operating model.
  • Cilium or Calico with BGP peering to top-of-rack switches, ECMP for Service traffic and optional native routing.
  • Local NVMe storage with local-path, TopoLVM or OpenEBS LocalPV, and Rook-Ceph where shared storage is needed.
  • Rack and zone topology labels so the scheduler spreads replicas across failure domains.
  • Optional KubeVirt for running remaining VMs alongside containers.

Day-2 operations

Day-2 support we provide

On bare metal, the hardware is part of the platform. Our support plans cover both.

Upgrades

Kubernetes and OS upgrades as rolling, image-based replacements, with firmware updates scheduled in the same maintenance cycle and validated on a canary server first.

Patching

Kernel, OS image, BMC firmware and NIC driver updates, tracked per hardware model so nothing is left on an old baseline.

Monitoring

Hardware health from BMC and SMART data, NVMe wear, BGP session state, temperatures and power, alongside normal cluster metrics.

Backup and DR

etcd snapshots, Velero backups and storage-level replication, plus documented bring-up of a whole rack from bare servers.

Scaling

Onboarding new servers by registering them and letting automation do the rest; capacity planning tied to your hardware lead times.

Incident response

Server and disk failures, BGP flaps, and kernel or driver regressions, coordinated with your data-centre remote hands when a part needs replacing.

Lessons learned

Common pitfalls we prevent

  • Hand-installed servers that cannot be rebuilt the same way twice.
  • Mixed firmware versions causing hard-to-reproduce NIC or disk issues.
  • Local volumes without replication, so a dead disk means lost data.
  • BGP misconfiguration that blackholes traffic during a switch upgrade.
  • Exposed BMC interfaces on the production network.
  • Very large nodes with too few servers, making each failure a big outage.

FAQ

Bare-metal questions

Related services: cluster build, platform engineering, AI infrastructure, and managed support.

Is bare metal always faster than VMs?
It removes the hypervisor overhead and gives direct access to devices, which matters most for storage-, network- and GPU-heavy work. For typical web services the difference is often small; the bigger gains are usually cost and licensing.
Why Talos Linux?
Talos is a minimal, immutable OS built only to run Kubernetes and managed entirely through an API. It removes SSH and configuration drift and makes upgrades predictable. It is not the only option; Flatcar or a hardened general-purpose distribution are fine when your team prefers them.
Do we need a hardware load balancer?
Usually not. With BGP-capable switches, Cilium, Calico or MetalLB can advertise Service addresses directly. Where BGP is not allowed, layer-2 mode is a simpler fallback with some failover limitations.
How many servers is the minimum?
Three for a highly available control plane, plus enough workers that losing one does not overload the rest. Small sites can combine control-plane and worker roles.
