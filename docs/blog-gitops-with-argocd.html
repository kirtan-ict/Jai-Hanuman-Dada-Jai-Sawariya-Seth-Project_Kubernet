GitOps with Argo CD: a working blueprint

GitOps makes Git the single source of truth for what runs in your clusters, and lets a controller continuously make reality match it. Argo CD is one of the most widely adopted ways to do that. Here is a blueprint that scales from one cluster to many.

  • Operations
  • 10 min read
  • By KubeSetu Engineering

Without GitOps, the state of a cluster is the sum of every kubectl apply, Helm install and hotfix anyone has ever run. Nobody can say with confidence what is deployed, why, or how to rebuild it. GitOps replaces that with four principles: the desired state is declarative, it is versioned and immutable in Git, it is pulled automatically by an agent in or near the cluster, and it is continuously reconciled, so drift is detected and corrected.

Argo CD implements those principles with a controller that compares Git with the live cluster, a UI and CLI for visibility, and building blocks for managing many applications and clusters. The tool is the easy part; most of the design work is in how you structure repositories and promotions.

Repository layout

Keep application source code and deployment configuration in separate repositories. CI builds and tests code, publishes an image, then updates the configuration repository with the new image reference. Argo CD watches only the configuration repository. This separation means a configuration change never triggers a code build, and access to production configuration can be controlled independently.

A layout that works well for a platform team managing shared add-ons alongside team applications:

gitops/
├── bootstrap/
│   └── root-app.yaml            # the one Application you apply by hand
├── platform/                    # cluster add-ons owned by the platform team
│   ├── cert-manager/
│   ├── ingress-nginx/
│   └── external-secrets/
├── apps/                        # one directory per application
│   ├── checkout/
│   │   ├── base/                # shared manifests (Kustomize base)
│   │   └── overlays/
│   │       ├── dev/
│   │       ├── staging/
│   │       └── prod/
│   └── search/
│       ├── base/
│       └── overlays/
└── appsets/
    ├── platform.yaml            # ApplicationSet for add-ons
    └── apps-prod.yaml           # ApplicationSet for production apps

Kustomize overlays and Helm values files both work well for environment differences. Choose one convention and stick to it; mixing styles per application makes reviews harder.

Prefer directories over branches for environments. Using a long-lived Git branch per environment sounds tidy but leads to painful merges and drift between branches. A directory per environment on a single main branch makes differences explicit and reviewable in one pull request.

Applications and sync policy

The core Argo CD resource is the Application: a source (a repository, revision and path) mapped to a destination (a cluster and namespace), plus a sync policy.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: checkout-prod
  namespace: argocd
spec:
  project: shop
  source:
    repoURL: https://git.example.com/platform/gitops.git
    targetRevision: main
    path: apps/checkout/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: checkout
  syncPolicy:
    automated:
      prune: true       # delete resources that were removed from Git
      selfHeal: true    # revert manual changes made in the cluster
    syncOptions:
      - CreateNamespace=true
    retry:
      limit: 5
      backoff:
        duration: 10s
        factor: 2
        maxDuration: 3m

Automated sync with selfHeal is what makes Git authoritative: if someone edits a Deployment by hand, Argo CD puts it back. Turn it on early for non-production environments. Some teams keep manual sync for production at first, then switch to automated once they trust their pipeline.

Group Applications into AppProjects to restrict which repositories, clusters, namespaces and resource kinds each team may deploy. Projects are the main multi-tenancy boundary in Argo CD, and they work together with Argo CD's own RBAC and single sign-on.

App-of-apps and ApplicationSets

Writing one Application by hand per service per environment does not scale. Two patterns solve this.

App-of-apps

A single "root" Application points at a directory that contains other Application manifests. You apply the root once; Argo CD creates and manages everything beneath it. This is a simple and effective way to bootstrap a cluster.

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.example.com/platform/gitops.git
    targetRevision: main
    path: appsets
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

ApplicationSets

An ApplicationSet generates Applications from a template and one or more generators. A Git directory generator creates one Application per matching directory; a cluster generator creates one per registered cluster; list and matrix generators combine dimensions. Adding a new application becomes as simple as adding a directory.

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: apps-prod
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - git:
        repoURL: https://git.example.com/platform/gitops.git
        revision: main
        directories:
          - path: apps/*/overlays/prod
  template:
    metadata:
      name: '{{index .path.segments 1}}-prod'
    spec:
      project: shop
      source:
        repoURL: https://git.example.com/platform/gitops.git
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{index .path.segments 1}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true

Here .path.segments splits the matched path, so apps/checkout/overlays/prod produces an Application called checkout-prod deploying into the checkout namespace. Generator features evolve between releases, so check the Argo CD documentation for the version you run.

Environments and promotion

Promotion in GitOps is a Git change. A typical flow looks like this:

  1. CI builds an image, tags it immutably (for example with the commit SHA) and pushes it.
  2. CI, or an image updater, opens or merges a change that sets the new tag in the dev overlay. Argo CD syncs it.
  3. After automated tests pass, a pull request copies the same tag to staging.
  4. After approval, a pull request promotes it to prod. The pull request is your change record and audit trail.
# apps/checkout/overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
images:
  - name: registry.example.com/shop/checkout
    newTag: 3f9c2e1     # promoted from staging by pull request
patches:
  - path: replicas.yaml

Keep environment overlays as thin as possible: replica counts, resource sizes, hostnames and feature flags. The more an environment differs from production, the less your testing there tells you.

Secrets without plain text in Git

Git history is forever, so secrets must never be committed in plain text. Three patterns are common:

  • External Secrets Operator: commit an ExternalSecret that references a key in a cloud secret manager or Vault. The operator creates the Kubernetes Secret in the cluster. Nothing sensitive touches Git.
  • Sealed Secrets: encrypt a Secret with a public key; only the controller in the target cluster can decrypt it.
  • SOPS: encrypt values in files with a KMS key or age, and decrypt during rendering through a plugin.
# Check the API version served by your External Secrets Operator release
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: checkout-db
  namespace: checkout
spec:
  refreshInterval: 1h
  secretStoreRef:
    kind: ClusterSecretStore
    name: cloud-secrets
  target:
    name: checkout-db         # the Kubernetes Secret that will be created
  data:
    - secretKey: password
      remoteRef:
        key: prod/checkout/db
        property: password

The external-manager approach is usually the easiest to operate at scale, because rotation happens in one place and audit logs live with the secret store. See our security checklist for the wider secrets picture.

Progressive delivery

Argo CD deploys whatever Git says, immediately. To release gradually and roll back automatically on bad metrics, add Argo Rollouts. A Rollout replaces a Deployment and adds canary or blue/green strategies, optionally driven by analysis against Prometheus or other metric providers.

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: checkout
  namespace: checkout
spec:
  replicas: 6
  selector:
    matchLabels:
      app: checkout
  template:
    metadata:
      labels:
        app: checkout
    spec:
      containers:
        - name: checkout
          image: registry.example.com/shop/checkout:3f9c2e1
          ports:
            - containerPort: 8080
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: {duration: 5m}
        - analysis:
            templates:
              - templateName: success-rate
        - setWeight: 50
        - pause: {duration: 10m}
        - setWeight: 100

Without a traffic router, the canary weight is approximated by the ratio of new to old pods. With an ingress controller, Gateway API implementation or service mesh integration, Rollouts can shift precise percentages of traffic. If the referenced AnalysisTemplate detects an elevated error rate, the rollout aborts and returns to the stable version.

Git and the cluster must agree after a rollback. An aborted rollout restores the stable version in the cluster, but Git still points at the bad image. Revert the change in Git too, otherwise the next sync or a fresh cluster will try the broken version again.

Operating Argo CD

  • Manage Argo CD itself through GitOps, with its configuration in the same repository and a documented bootstrap procedure.
  • Decide between one Argo CD instance managing many clusters (simpler, central visibility) and one per cluster or region (smaller blast radius). Both are valid.
  • Use SSO for the UI and CLI, and map groups to AppProjects with least-privilege roles.
  • Alert on applications that are out of sync or degraded for longer than a threshold; Argo CD exposes Prometheus metrics for this.
  • Rehearse rebuilding a cluster from Git. It is the best proof that your GitOps setup is complete, and it turns disaster recovery and blue/green cluster upgrades into routine operations.

Key takeaways

  • Separate application source from deployment configuration, and let Argo CD watch only configuration.
  • Use a directory per environment on one main branch rather than a branch per environment.
  • Enable automated sync with prune and self-heal so Git stays authoritative, and use AppProjects as tenancy boundaries.
  • Bootstrap with app-of-apps and scale with ApplicationSets and generators.
  • Promote by pull request with immutable image tags; the history is your audit trail.
  • Keep secrets out of Git with External Secrets, Sealed Secrets or SOPS.
  • Add Argo Rollouts for canaries with automated analysis, and revert Git when a rollout aborts.
