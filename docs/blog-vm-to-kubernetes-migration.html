Migrating VM and legacy workloads to Kubernetes

Moving to Kubernetes is not a lift-and-shift exercise with a new logo. Done well, it is a sequence of small, reversible steps that start with understanding what you run and end with a cutover nobody notices.

  • Migration
  • 10 min read
  • By KubeSetu Engineering

Most organisations arrive at Kubernetes with a mixed estate: a few modern services that already run in containers, a large middle of applications on virtual machines that were never designed for orchestration, and a long tail of packaged software, scheduled scripts and databases. Treating all of that as one migration project is the fastest route to a stalled programme.

The approach below breaks the work into phases. Each phase produces something useful on its own, and each cutover keeps a clear path back.

Start with why

Write down the outcomes you expect before you inventory anything. Typical goals include faster and safer releases, higher infrastructure utilisation, consistent operations across environments, or getting off ageing hypervisor licences and hardware. These goals decide which applications move first and what "done" looks like. They also tell you when not to migrate something: if an application changes once a year and runs happily on a VM, moving it may cost more than it returns.

Assess the portfolio

For each application, collect enough information to make a decision, not a perfect model. A spreadsheet is fine.

DimensionWhat to capture
RuntimeLanguage, framework, OS dependencies, licensing constraints
StateLocal disk writes, databases, file shares, session storage, caches
DependenciesUpstream and downstream services, hard-coded hostnames or IPs, shared libraries
ConfigurationWhere config lives, how secrets are delivered, environment differences
OperationsHow it is deployed, monitored, backed up and scaled today
BusinessOwner, criticality, change frequency, maintenance windows, compliance needs

Dependency mapping deserves real effort. Network flow logs, APM traces and a conversation with the people who get paged for each system usually reveal connections that no diagram shows. Hidden dependencies, such as a nightly job that writes to another application's database, are the most common reason a cutover has to be rolled back.

Score each application on two axes: business value of moving and technical difficulty. Your first wave should be valuable enough to matter and easy enough to succeed; it is where you build the platform, the pipelines and the team's confidence.

Choose a path with the 6Rs

The "6Rs" are a common vocabulary for migration decisions. Assign one to each application:

  • Rehost (lift and shift): move the workload largely unchanged. On Kubernetes this can mean running the VM itself with KubeVirt or an equivalent virtualisation layer, which lets you consolidate platforms before modernising.
  • Replatform (lift, tinker and shift): containerise the application with minimal code changes, externalise configuration, and swap a self-run database for a managed one. This is the most common path to Kubernetes.
  • Refactor (re-architect): change the application to be cloud native, for example splitting a monolith or making it stateless. Highest effort, highest long-term payoff, best done incrementally.
  • Repurchase: replace the application with a SaaS product or a vendor-supplied container version.
  • Retire: switch it off. Assessments routinely turn up applications nobody uses.
  • Retain: leave it where it is for now, perhaps because of licensing, hardware ties or low value.
Be explicit about Retain and Retire. A migration programme that claims to move everything will stall on the hardest few percent. Deciding early what stays, and what goes away, keeps momentum on the work that matters.

Containerise properly

A container image should be small, reproducible and free of environment-specific settings. A multi-stage build keeps build tools out of the runtime image:

# Build stage: compile with the full toolchain
FROM maven:3-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q package -DskipTests

# Runtime stage: only the JRE and the application
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/target/app.jar /app/app.jar
USER 10001
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

Base image tags are illustrative; pin the versions your organisation supports, ideally by digest. Beyond the Dockerfile, a containerised application needs a few behaviours that VMs often lacked:

  • Configuration from the environment. Move settings into ConfigMaps and secrets into an external secret store, rather than baking them into images or files on disk.
  • Logs to stdout and stderr. Let the platform collect logs instead of writing rotating files inside the container.
  • Health endpoints. Expose liveness and readiness checks so Kubernetes knows when to restart the process and when to send traffic.
  • Graceful shutdown. Handle SIGTERM, stop accepting new work and finish in-flight requests.
  • Non-root execution. Run as an unprivileged user so the workload can meet the restricted Pod Security Standard (see our security checklist).
apiVersion: apps/v1
kind: Deployment
metadata:
  name: billing
  namespace: billing
spec:
  replicas: 3
  selector:
    matchLabels:
      app: billing
  template:
    metadata:
      labels:
        app: billing
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: billing
          image: registry.example.com/billing/billing:1.0.0
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: billing-config
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
          resources:
            requests:
              cpu: 500m
              memory: 768Mi
            limits:
              memory: 1Gi

Handle stateful data

Stateless application tiers are the easy part. Data needs its own plan:

  • Prefer managed data services where they exist and meet your requirements. Moving a database to a managed service is often a separate, earlier migration that de-risks the application move.
  • Run databases on Kubernetes deliberately, using a mature operator, StatefulSets and a CSI storage class with the right performance and snapshot support. Have tested backup and restore before production data arrives.
  • Plan data synchronisation for cutover. Native replication, change data capture or a final dump-and-restore during a short write freeze are the usual options. Rehearse with production-sized data to measure real timings.
  • Find local state. Uploaded files on local disk, in-memory sessions and file-based caches must move to object storage, a shared volume or a cache service before the application can scale horizontally.
Rehearse the data move. Synchronisation and cutover timings measured on a test dataset rarely match production. Run at least one full rehearsal with realistic volumes, and time the rollback path too.

Cutover strategies

Pick the cutover style per application based on risk and how well the old and new versions can coexist.

  • Big bang: stop the old system, migrate, start the new one. Simple, and acceptable for low-criticality systems with an agreed maintenance window.
  • Blue/green: run both environments and switch traffic at the load balancer or DNS layer. Switching back is fast as long as data has not diverged.
  • Weighted or canary: send a small percentage of traffic to the Kubernetes version, watch error rates and latency, and increase gradually.
  • Strangler fig: place a routing layer in front of a monolith and move one route or capability at a time to new services on Kubernetes. Ideal for large applications you are refactoring incrementally.
  • Parallel run: process the same inputs in both systems and compare outputs before switching. Useful for batch and financial workloads where correctness must be proven.

During a transition, workloads on Kubernetes often need to call services still running on VMs. A Service without a selector, paired with an EndpointSlice, gives those VMs a stable in-cluster name, so application configuration does not change when the backend later moves into the cluster:

apiVersion: v1
kind: Service
metadata:
  name: legacy-ledger
  namespace: billing
spec:
  ports:
    - name: http
      port: 80
      protocol: TCP
---
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: legacy-ledger-vms
  namespace: billing
  labels:
    kubernetes.io/service-name: legacy-ledger
addressType: IPv4
ports:
  - name: http
    port: 8080
    protocol: TCP
endpoints:
  - addresses: ["10.20.30.41"]
  - addresses: ["10.20.30.42"]

Pods can now call http://legacy-ledger.billing. When the ledger itself migrates, replace the EndpointSlice with a normal selector-based Service and the callers never notice.

After the move

Keep the old environment available, but idle, until the new one has run through a full business cycle: month-end processing, peak traffic, backups and a restore test. Then decommission it properly, removing DNS records, firewall rules and credentials. Finally, feed what you learned back into the plan for the next wave; each wave should be faster than the last. A GitOps workflow, described in our Argo CD guide, makes migrated applications reproducible from day one.

Key takeaways

  • Define the business outcomes first; they decide what moves, in what order, and what stays.
  • Invest in dependency mapping; hidden dependencies cause most failed cutovers.
  • Assign one of the 6Rs to every application, and be explicit about Retain and Retire.
  • Containerise with externalised config, stdout logging, health probes, graceful shutdown and non-root users.
  • Plan stateful data separately, prefer managed services, and rehearse synchronisation with real volumes.
  • Choose a cutover style per application and always keep a tested route back.
