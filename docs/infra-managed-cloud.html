Managed cloud Kubernetes

EKS, AKS and GKE, built properly from day one

The cloud provider runs the control plane. Everything around it is still yours to get right: the network, identity, node pools, autoscaling, add-ons and upgrades. We build that foundation as code and then help you run it.

  • Amazon EKS
  • Azure AKS
  • Google GKE
  • Oracle OKE
  • DigitalOcean DOKS
  • Linode / Akamai LKE

When this fits

  • You already run most workloads in one public cloud, or plan to.
  • You want to spend engineering time on applications, not on etcd and control-plane patching.
  • Traffic is variable and you benefit from elastic node capacity and spot pricing.
  • You need tight integration with cloud IAM, load balancers, managed databases and KMS.
  • A small platform team has to support many product teams.

When it doesn't

  • Data must stay on hardware you own, or in a location no provider region covers.
  • Sites have no reliable internet connection (see edge or air-gapped).
  • Steady, predictable, very large compute where owned hardware is cheaper over its life (see bare metal).
  • You need control-plane flags or versions that the provider does not expose.
  • Egress-heavy workloads where data-transfer charges dominate the bill.
Reference architecture

The layers we design

A managed control plane removes one hard problem, not all of them. Most production incidents we see on managed clusters come from the layers around it: an IP range that ran out, a node group that could not scale, a pod with cloud-admin rights, or an add-on that was never upgraded.

  • Landing zone first. Accounts, subscriptions or projects separated by environment, with guardrails and central logging.
  • Network sized for growth. Subnet and pod CIDR planning that leaves room for more nodes, more clusters and peering.
  • Least-privilege identity. Each workload gets its own cloud role through IRSA, EKS Pod Identity, AKS Workload Identity or GKE Workload Identity, never node-wide credentials.
  • Separated node pools. System components isolated from application and spot capacity.
Implementation

What we implement

  • Landing zone or account structure: AWS Organizations, Azure management groups or GCP folders, with guardrail policies.
  • VPC / VNet design: zones, subnets, private endpoints, NAT, peering or transit, and pod IP strategy (VPC CNI, Azure CNI Overlay, GKE VPC-native).
  • Private or restricted API endpoints and admin access through SSO.
  • Workload-level cloud identity (IRSA / EKS Pod Identity, Workload Identity on AKS and GKE).
  • Node pools by purpose, with taints, labels and instance families matched to workloads.
  • Autoscaling with Karpenter or Cluster Autoscaler, plus HPA and, where useful, KEDA.
  • Managed add-ons kept on supported versions: CNI, CoreDNS, kube-proxy, CSI drivers.
  • Ingress or Gateway API with cloud load balancers, cert-manager and external-dns.
  • Everything as code in Terraform or OpenTofu, delivered through GitOps.

Day-2 operations

Day-2 support we provide

Managed control planes still need an owner. These are the recurring jobs we take on under a support plan.

Upgrades

Providers retire Kubernetes versions on a fixed schedule. We plan each minor upgrade ahead of the deadline, check deprecated APIs, upgrade add-ons in the right order and roll node pools with surge capacity.

Patching

Node image refreshes for OS and kernel fixes, add-on patch releases, and quick response when a CVE affects the CNI, ingress controller or runtime.

Monitoring

Control-plane and node health, API latency, pod restarts, IP exhaustion, quota limits and certificate expiry, with alerts routed to people who can act.

Backup and DR

Velero backups of cluster objects and volumes, cross-region copies, and rebuild-from-code drills so a lost cluster becomes a re-deploy, not a rescue.

Scaling and cost

Karpenter or autoscaler tuning, consolidation, spot interruption handling, rightsizing requests, and commitment planning with your finance team.

Incident response

Triage and fix for failing nodes, stuck rollouts, DNS issues and load-balancer problems, plus working the provider support case on your behalf when the fault is theirs.

Lessons learned

Common pitfalls we prevent

  • Pod IP exhaustion from subnets sized for nodes rather than pods.
  • Falling off the support window and being force-upgraded, or moved to paid extended support, without testing.
  • Node-wide cloud credentials that let any pod reach every bucket or database.
  • A public API endpoint left open to the internet with no IP restrictions.
  • One big node group where a noisy batch job starves CoreDNS and ingress.
  • Surprise data-transfer bills from cross-zone traffic and NAT gateway processing.
  • ClickOps clusters that nobody can reproduce after a mistake.

FAQ

Managed cloud questions

Related services: cluster build, migration, FinOps, security, and ongoing support.

Which is best: EKS, AKS or GKE?
All three are mature. The right one is usually the cloud where your data, identity and existing contracts already live. GKE tends to offer the most automation out of the box, AKS integrates closely with Entra ID and Azure networking, and EKS has the broadest ecosystem on AWS. We are happy to work on any of them.
Do we still need to upgrade if the provider manages the control plane?
Yes. You choose when to upgrade within the support window, and you are responsible for node pools, add-ons and any deprecated APIs your manifests use. If you wait too long, providers either upgrade you automatically or charge for extended support.
Should we use Karpenter or Cluster Autoscaler?
On EKS, Karpenter is generally the better choice for mixed instance types and spot. Cluster Autoscaler remains a solid option everywhere and is what AKS and GKE build on. We pick based on your provider, workload shape and how much instance diversity you want.
Are Autopilot or Auto Mode a good idea?
They suit teams that want minimal node management and can live within their constraints on privileged workloads and node customisation. We assess your workloads against those limits before recommending them.
Can you work in our existing cloud accounts?
Yes. We usually work inside your accounts with scoped, audited roles, and leave all code in your repositories.
