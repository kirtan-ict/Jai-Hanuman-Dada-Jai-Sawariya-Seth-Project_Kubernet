Hybrid and multi-cloud

One operating model across clouds and data centres

Clusters in more than one place are now normal: a data centre plus a cloud, two clouds, or several regions. We make them behave as one estate, with the same provisioning, the same policies and a tested plan for losing any one of them.

When this fits

  • Some data must stay on-premises while customer-facing services run in the cloud.
  • Recovery targets require surviving the loss of a whole region or provider.
  • Acquisitions or team history have left you with clusters on several platforms.
  • Customers or regulators require workloads in specific countries or clouds.
  • You want to burst into the cloud for peaks while keeping a steady on-premises base.

When it doesn't

  • "Avoiding lock-in" is the only reason. Running two clouds well usually costs more than the lock-in it avoids.
  • Your applications are not yet stateless or portable; fix that first.
  • The team is still learning to run one cluster well. Start with one managed cloud and add locations later.
  • Cross-site latency would sit on the hot path of every request.
Reference architecture

Same platform, different places

The hard part of hybrid is not connecting clusters; it is keeping them consistent. We separate what must be the same everywhere (identity, policy, delivery, observability) from what may differ (node types, storage, load balancers) and encode both.

  • One provisioning API: Cluster API or a vendor control plane describes every cluster the same way.
  • One delivery path: GitOps targets clusters by labels such as region, provider and tier.
  • One policy set: admission policies and RBAC applied everywhere from the same source.
  • Explicit failover: health-based global routing and data replication with known recovery point and time.
Implementation

What we implement

  • Placement strategy: which workloads run where, and why, documented as a decision record.
  • Fleet management with Cluster API, Rancher, Azure Arc-enabled Kubernetes, GKE Enterprise fleets, or EKS Anywhere and EKS Hybrid Nodes.
  • Private connectivity: VPN, Direct Connect, ExpressRoute or Cloud Interconnect, with non-overlapping IP plans.
  • Multi-cluster service networking with Cilium Cluster Mesh, Submariner or a service mesh where needed.
  • Global traffic management using DNS-based load balancing, health checks and weighted or geo routing.
  • Centralised identity (OIDC) and policy-as-code applied identically to every cluster.
  • Cross-region and cross-cloud backup with Velero, plus data replication patterns for databases.
  • Disaster-recovery runbooks and scheduled failover exercises.

Day-2 operations

Day-2 support we provide

More locations mean more moving parts. Our support plans keep the estate consistent and recoverable.

Upgrades

Coordinated upgrades across providers whose version calendars differ, keeping all clusters within a narrow, supported version range.

Patching

Platform and add-on patches promoted through the same GitOps waves everywhere, with drift reports for clusters that fall behind.

Monitoring

Backup and DR

Backups replicated to another site or provider, and regular failover drills that measure real recovery time against your targets.

Scaling

Adding regions or clusters from templates, capacity bursting into the cloud, and placement reviews as costs and regulations change.

Incident response

Regional or provider outages handled with prepared failover steps, plus diagnosis of cross-cluster networking and DNS issues.

Lessons learned

Common pitfalls we prevent

  • Overlapping IP ranges that make clusters impossible to connect later.
  • Lowest-common-denominator design that throws away every useful cloud feature.
  • A DR site that was never tested and quietly drifted out of date.
  • Unplanned egress costs from chatty services split across providers.
  • Different policies per cluster so a workload is allowed in one place and blocked in another.
  • A single management plane that becomes the new single point of failure.

FAQ

Hybrid and multi-cloud questions

Related services: strategy and assessment, reliability and DR, GitOps, policy and security, and support.

Should we use a vendor control plane or open source?
Azure Arc, GKE Enterprise and Rancher give you a ready-made management experience and support, tied to that vendor. Cluster API with GitOps is fully open and portable but needs more in-house skill. Many organisations mix them: open-source delivery and policy, with a vendor tool for visibility.
Do we need a service mesh for multi-cluster?
Not always. If services only need to reach each other across clusters, Cilium Cluster Mesh or Submariner is often enough. A mesh is worth it when you also need mTLS everywhere, fine-grained traffic shifting or rich per-request telemetry.
What about stateful data?
Kubernetes can move stateless workloads easily; data is the hard part. We use database-native replication or managed database services per site, and we agree on realistic recovery point objectives before choosing a pattern.
Is active-active across clouds realistic?
For stateless, read-heavy services it can be. For write-heavy systems it adds significant complexity, and active-passive with tested failover is often the better trade-off.
