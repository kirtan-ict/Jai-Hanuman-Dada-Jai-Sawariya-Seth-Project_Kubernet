A production Kubernetes security checklist

Kubernetes is flexible by design, and many of its defaults favour getting started over locking down. This checklist walks through the controls we expect on any production cluster, layer by layer, with configuration you can adapt.

  • Security
  • 10 min read
  • By KubeSetu Engineering

Security in Kubernetes is a stack of overlapping controls. No single one is sufficient, and each covers a gap the others leave. An attacker who gets code execution inside a container should find that the container runs as an unprivileged user, cannot reach most of the network, holds no useful credentials, cannot talk to the API server with meaningful permissions, and that their activity is being noticed.

We have grouped the checklist into the layers where we most often find gaps during cluster reviews. Work through them in order; earlier items tend to be cheaper to fix and reduce more risk.

1. API access and RBAC

The Kubernetes API is the front door to everything. Control who can reach it and what they can do once inside.

  • The API endpoint is private, or restricted to known networks, wherever your platform allows it.
  • Humans authenticate through your identity provider (OIDC or the cloud's IAM integration), never with shared certificates or static tokens.
  • Nobody uses cluster-admin for daily work; break-glass access is audited and time-limited.
  • Permissions are granted to groups, not individuals, and scoped to namespaces with Roles and RoleBindings wherever possible.
  • Wildcards (*) in verbs or resources are treated as findings, and access to secrets, pods/exec and escalate/bind/impersonate verbs is reviewed explicitly.
  • Workloads use dedicated ServiceAccounts, and pods that do not call the API set automountServiceAccountToken: false.

A narrowly scoped role for a team that deploys applications into its own namespace might look like this:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: app-deployer
  namespace: payments
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["services", "configmaps"]
    verbs: ["get", "list", "watch", "create", "update", "patch"]
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: payments-team-deployers
  namespace: payments
subjects:
  - kind: Group
    name: payments-engineers
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: app-deployer
  apiGroup: rbac.authorization.k8s.io

Verify what an identity can actually do rather than reading YAML and guessing:

kubectl auth can-i --list --namespace payments --as=system:serviceaccount:payments:checkout
kubectl auth can-i get secrets --all-namespaces --as=jane@example.com

2. Pod Security Standards

Pod Security Standards define three profiles: privileged, baseline and restricted. The built-in Pod Security Admission controller enforces them per namespace through labels. Aim for restricted on application namespaces and reserve exceptions for system components that genuinely need host access.

apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted

A container spec that satisfies the restricted profile sets an explicit security context:

securityContext:          # pod level
  runAsNonRoot: true
  seccompProfile:
    type: RuntimeDefault
containers:
  - name: app
    image: registry.example.com/payments/checkout@sha256:REPLACE_WITH_DIGEST
    securityContext:      # container level
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
Roll out gradually. Apply the warn and audit labels first. You will see which workloads would be rejected without breaking anything, then fix them before switching on enforce.

For rules beyond what Pod Security covers, such as requiring resource requests, approved registries or specific labels, add a policy engine like Kyverno or OPA Gatekeeper, or use the built-in ValidatingAdmissionPolicy with CEL expressions.

3. Network policies

By default, every pod can talk to every other pod in the cluster. Network policies let you change that, but only if your CNI enforces them. Check that it does before relying on them.

  • Each application namespace has a default-deny policy for ingress, and ideally for egress.
  • Allow rules are explicit and minimal: which pods, which ports, from where.
  • Egress to the cloud metadata endpoint is blocked for workloads that do not need it.
  • DNS egress is explicitly allowed, otherwise default-deny egress will break name resolution.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: payments
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: payments
spec:
  podSelector: {}
  policyTypes: ["Egress"]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: checkout-from-ingress
  namespace: payments
spec:
  podSelector:
    matchLabels:
      app: checkout
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: ingress-nginx
      ports:
        - protocol: TCP
          port: 8080

The DNS pod label varies by distribution, so confirm it in your cluster. For layer 7 rules, mutual TLS between services or identity-aware policies, consider a service mesh or a CNI with extended policy support.

4. Secrets management

Kubernetes Secrets are base64-encoded, not encrypted, unless you configure encryption at rest. Treat them accordingly.

  • Encryption at rest for Secrets is enabled, preferably with a KMS provider so keys live outside the cluster.
  • The source of truth for secrets is an external manager (a cloud secrets service or Vault), synced in with the External Secrets Operator or mounted with the Secrets Store CSI Driver.
  • Plain-text secrets never live in Git. If you use GitOps, store only encrypted or reference objects (see our Argo CD guide).
  • Secrets are mounted as files rather than environment variables where possible, since environment variables leak more easily into logs and crash dumps.
  • Cloud access uses workload identity federation instead of long-lived keys.
  • Rotation is automated and tested.

5. Image supply chain: signing and SBOMs

You should be able to answer two questions about every running container: where did this image come from, and what is inside it?

  • Images come from a small set of approved registries, and admission policy rejects anything else.
  • Deployments reference images by digest, or tags are immutable in your registry.
  • CI scans images for known vulnerabilities and fails builds above an agreed severity threshold.
  • CI generates a Software Bill of Materials (SBOM) in SPDX or CycloneDX format and attaches it to the image.
  • Images are signed in CI (for example with Sigstore cosign), and admission policy verifies signatures before pods run.
  • Base images are minimal (distroless or slim) and rebuilt regularly.
# In CI: generate an SBOM, sign the image and attach the SBOM as a signed attestation
syft registry.example.com/payments/checkout@sha256:REPLACE_WITH_DIGEST -o spdx-json > sbom.spdx.json
cosign sign --yes registry.example.com/payments/checkout@sha256:REPLACE_WITH_DIGEST
cosign attest --yes --type spdxjson --predicate sbom.spdx.json \
  registry.example.com/payments/checkout@sha256:REPLACE_WITH_DIGEST

The commands above use keyless signing, which ties signatures to your CI system's identity. Signing alone achieves nothing unless something verifies it; configure an admission policy (Kyverno's image verification rules or the Sigstore policy controller) that checks signatures against your expected signer identity. Flags and defaults evolve, so follow the tools' current documentation.

6. Runtime detection and audit logging

Preventive controls reduce risk; detective controls tell you when prevention failed.

  • API server audit logging is enabled and shipped to a central, tamper-resistant store, with a policy that captures access to secrets, RBAC changes and exec sessions.
  • A runtime security tool such as Falco or Tetragon watches system calls for suspicious behaviour: shells in containers, unexpected outbound connections, writes to sensitive paths.
  • Alerts route to people who are on call and know what to do with them.
  • You have an incident runbook covering how to isolate a pod (for example with a quarantine network policy), preserve evidence and rotate credentials.
Alert fatigue is a security risk. A detection tool that fires hundreds of untriaged alerts a day is effectively switched off. Start with a small set of high-signal rules and tune them before expanding.

7. Node hardening and the CIS benchmark

The CIS Kubernetes Benchmark is a widely used set of configuration recommendations for control plane components, etcd, kubelets and policies. Managed providers publish their own variants, because you cannot change control plane settings they own.

  • Run a benchmark scanner such as kube-bench periodically and track results over time.
  • Kubelet anonymous authentication is disabled and authorisation uses webhook mode.
  • Nodes run a minimal, regularly patched operating system; container-optimised OS images help here.
  • SSH to nodes is disabled or tightly controlled; access goes through audited tooling.
  • The instance metadata service is protected (for example, requiring session tokens and limiting hop counts on AWS).
# Run kube-bench as a one-off Job (manifests are published in the kube-bench repository;
# pick the one that matches your platform) and read the results
kubectl apply -f job.yaml
kubectl logs job/kube-bench

Treat benchmark output as a prioritised to-do list, not a pass/fail grade. Some findings will not apply to your platform, and documenting why is part of the exercise. For regulated environments, map these controls to your compliance framework early; it is much easier than retrofitting evidence later.

Key takeaways

  • Lock down API access first: private endpoints, SSO, least-privilege RBAC and no daily use of cluster-admin.
  • Enforce the restricted Pod Security Standard on application namespaces, rolling out via warn and audit modes.
  • Default-deny network traffic per namespace, and confirm your CNI actually enforces policy.
  • Keep secrets in an external manager, encrypt them at rest, and never commit plain text to Git.
  • Sign images, generate SBOMs and verify both at admission time.
  • Turn on audit logging and runtime detection, and make sure alerts reach a human.
  • Benchmark nodes against CIS regularly and track remediation like any other backlog.
