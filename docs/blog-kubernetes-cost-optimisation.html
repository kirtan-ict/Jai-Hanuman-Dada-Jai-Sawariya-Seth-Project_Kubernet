Cutting Kubernetes cost without cutting reliability

Kubernetes makes it easy to request capacity and hard to see who is using it. Most savings come not from exotic tricks but from three habits: request what you need, scale with demand, and make cost visible to the people who create it.

  • Cost
  • 9 min read
  • By KubeSetu Engineering

The scheduler places pods based on their requests, not on what they actually use. If a pod requests two CPUs and uses a tenth of one, the node still reserves two CPUs for it, and the cluster autoscaler still buys nodes to fit that reservation. Across hundreds of workloads, that gap between requested and used capacity is usually the biggest line in the bill, and it is invisible unless you look for it.

This guide works from the pod outward: first rightsize individual workloads, then make them scale, then make the nodes underneath match, and finally build the visibility that keeps savings from eroding.

Measure before you cut

Start by comparing requests with real usage. You need a metrics pipeline (metrics-server for a quick look, Prometheus or a managed equivalent for history). A week or two of data covering normal peaks is the minimum before changing anything.

# Live usage per pod (requires metrics-server)
kubectl top pods -A --sort-by=cpu

# Requested vs allocatable capacity per node
kubectl describe nodes | grep -A 8 "Allocated resources"

With Prometheus, compare the 95th percentile of usage with requests per container. The PromQL below is a starting point; adjust label names to match your exporters.

# CPU requested but unused, by namespace (cores)
sum by (namespace) (kube_pod_container_resource_requests{resource="cpu"})
-
sum by (namespace) (rate(container_cpu_usage_seconds_total{container!=""}[5m]))

Rightsize requests and limits

Requests determine scheduling and your bill; limits determine what happens under pressure. Set them deliberately:

  • CPU requests should track typical usage with modest headroom. CPU is compressible: a container that exceeds its request is simply throttled relative to others when the node is busy.
  • CPU limits are optional and often counter-productive for latency-sensitive services, because they throttle even when the node has idle CPU. Many teams omit them and rely on accurate requests instead. Decide per workload.
  • Memory requests should cover realistic peak usage. Memory is not compressible; a pod that exceeds its memory limit is killed.
  • Memory limits are usually set equal to, or slightly above, the request to avoid noisy-neighbour surprises and node-level memory pressure.
resources:
  requests:
    cpu: 250m
    memory: 384Mi
  limits:
    memory: 512Mi    # no CPU limit: avoid throttling when the node has spare CPU

Use namespace-level guardrails so that new workloads start with sensible defaults and teams cannot accidentally claim a whole node:

apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: catalogue
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
        memory: 128Mi
      default:
        memory: 256Mi
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: catalogue
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.memory: 60Gi

Scale pods with HPA and VPA

The Horizontal Pod Autoscaler (HPA) changes the number of replicas based on observed metrics. It is the right tool for stateless services whose load varies through the day.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: search-api
  namespace: catalogue
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: search-api
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300

CPU utilisation in an HPA is calculated relative to the pod's request, so rightsizing and horizontal scaling go hand in hand. For queue workers and event-driven jobs, KEDA can scale on queue depth or other external signals, including to zero.

The Vertical Pod Autoscaler (VPA) recommends, and optionally applies, better requests based on observed usage. Running it in recommendation-only mode is a low-risk way to get rightsizing suggestions for every workload:

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: search-api
  namespace: catalogue
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: search-api
  updatePolicy:
    updateMode: "Off"   # recommend only; read with: kubectl describe vpa search-api -n catalogue
Do not let HPA and VPA fight. If both act on the same resource metric (for example CPU) for the same workload, they will work against each other. A common pattern is HPA on CPU or a custom metric, with VPA in recommendation mode feeding periodic manual or automated request updates.

Scale nodes: Cluster Autoscaler or Karpenter

Pod autoscaling only saves money if nodes follow. Two approaches dominate:

  • Cluster Autoscaler adds nodes to predefined node groups when pods are pending and removes underutilised nodes. It works on every major cloud and is well understood, but it is limited to the instance shapes you defined in each group.
  • Karpenter provisions nodes directly from pending pod requirements, choosing from a wide range of instance types, and continually consolidates workloads onto fewer or cheaper nodes. It originated on AWS and has providers for other platforms, including Azure.

A Karpenter NodePool that allows both spot and on-demand capacity across architectures, with consolidation enabled, looks roughly like this. API versions and fields have changed across releases, so check the documentation for the version you install.

apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64", "arm64"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m
  limits:
    cpu: "200"

Whichever you choose, set a hard upper limit on cluster size. Autoscalers will happily follow a runaway deployment all the way to your quota.

Use spot capacity safely

Spot (or preemptible) instances are spare cloud capacity sold at a discount, with the catch that the provider can reclaim them at short notice. They suit stateless services with several replicas, batch jobs and CI runners. They do not suit single-replica databases.

  • Diversify across many instance types and zones so a single capacity shortage does not take out a whole tier.
  • Handle interruption notices: Karpenter and the cloud providers' node termination handlers can cordon and drain nodes before they disappear.
  • Keep a baseline on on-demand capacity for critical services, and use node affinity or taints to steer workloads.
  • Make sure PodDisruptionBudgets and graceful shutdown are in place, exactly as for upgrades.

Bin packing and idle resources

Once requests are honest, nodes can be packed more densely. A few levers help:

  • Fewer, larger node shapes reduce per-node overhead (system daemons, kubelet reservations) as a proportion of capacity, although very large nodes increase the blast radius of a node failure.
  • Consolidation by Karpenter, or a lower scale-down utilisation threshold for Cluster Autoscaler, moves pods off underused nodes.
  • Scheduler scoring on self-managed clusters can favour packing (a "most allocated" strategy) over spreading; managed services expose this to varying degrees.
  • Arm-based instances often offer better price-performance if your images are built for multiple architectures.

Then hunt for capacity nobody is using:

  • Development and preview namespaces that run around the clock. Scale them to zero out of hours with a scheduled job or a tool such as kube-downscaler.
  • Orphaned PersistentVolumes and snapshots left behind after workloads were deleted.
  • Load balancers created by forgotten Services of type LoadBalancer.
  • Over-provisioned logging: high-volume debug logs shipped and stored at production retention.
# Volumes not bound to any claim
kubectl get pv | grep -E "Released|Available"

# Every Service that provisions a cloud load balancer
kubectl get svc -A | awk 'NR==1 || $3=="LoadBalancer"'

# Scale a non-production namespace's deployments to zero for the night
kubectl scale deployment --all --replicas=0 -n preview-feature-123

Cost visibility with OpenCost

Savings erode when nobody can see what their workloads cost. OpenCost, a CNCF project, allocates cluster cost to namespaces, deployments, labels and pods using cloud pricing data or custom rates for on-premises hardware. It exposes the results through an API, a UI and Prometheus metrics.

  • Label every workload with owner, team and cost centre, and enforce those labels with admission policy.
  • Publish a weekly cost report per team; even simple visibility changes behaviour.
  • Show idle cost (capacity paid for but not requested) separately, so platform teams own it explicitly.
  • Feed cost into the same dashboards as reliability, so trade-offs are visible together.
Make it a practice, not a project. One-off clean-ups decay within months. A regular review of rightsizing recommendations, idle resources and unit cost per service keeps the gains. Our cost estimator is a useful starting point for planning.

Key takeaways

  • The gap between requested and used resources is usually the largest source of waste; measure it first.
  • Set memory requests and limits carefully, and consider dropping CPU limits for latency-sensitive services.
  • Use HPA for variable load and VPA in recommendation mode for rightsizing, without letting them fight over the same metric.
  • Let a node autoscaler such as Cluster Autoscaler or Karpenter follow demand, with consolidation and a hard size cap.
  • Use diversified spot capacity for resilient, replicated workloads and handle interruptions gracefully.
  • Scale idle environments to zero and clean up orphaned volumes and load balancers.
  • Give every team visibility of its own cost with OpenCost and consistent labelling.
