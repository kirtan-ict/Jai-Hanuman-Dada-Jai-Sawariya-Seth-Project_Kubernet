The zero-downtime Kubernetes upgrade playbook

Kubernetes ships new minor versions several times a year, and each one has a finite support window. Upgrades are not optional, so the goal is to make them routine, predictable and invisible to your users.

  • Operations
  • 10 min read
  • By KubeSetu Engineering

Most upgrade incidents are not caused by Kubernetes itself. They come from things around it: a manifest that still uses an API version the new release no longer serves, an add-on that was never tested against the new version, or a workload with a single replica and no disruption budget that disappears while its node drains. A good playbook turns each of those risks into a check you run before anything changes.

This playbook applies to managed services (EKS, AKS, GKE) and to self-managed clusters built with tools like kubeadm. The mechanics of clicking "upgrade" differ; the discipline does not.

Understand the version rules

Kubernetes has a documented version skew policy. The details are in the upstream documentation and you should read the current version, but the principles that shape every upgrade plan are stable:

  • Upgrade one minor version at a time. Skipping minor versions on the control plane is not supported. If you are several versions behind, plan a sequence of upgrades.
  • Control plane first, then nodes. The kubelet must never be newer than the API server. Nodes may lag the control plane by a limited number of minor versions, which is what gives you room to upgrade node pools gradually.
  • Clients have a skew window too. Keep kubectl, CI tooling and controllers within the supported range of the API server.
Check the release notes every time. Each Kubernetes release, and each managed provider, publishes notes covering removed APIs, changed defaults and feature gate graduations. Read them for every version you pass through, not only the final target.

Pre-flight checks

Run these at least a week before the maintenance window, so you have time to fix what they find:

  1. Cluster health. All nodes Ready, no pods stuck in CrashLoopBackOff or Pending for unexplained reasons, and control plane components healthy.
  2. Backups you have actually restored. For self-managed clusters, take an etcd snapshot. On any cluster, back up resources and persistent volumes with a tool such as Velero, and prove the restore path works in a scratch cluster.
  3. Add-on compatibility. List every controller and operator: CNI, CSI drivers, ingress, cert-manager, service mesh, policy engines, autoscalers, monitoring agents. Confirm each supports the target version, and upgrade them first if needed.
  4. Capacity headroom. Surge and blue/green strategies temporarily add nodes. Confirm quotas, IP address space and budget allow it.
  5. Change freeze and communication. Agree a window, an owner, a rollback decision point and a status channel.
# Quick health snapshot before you start
kubectl get nodes -o wide
kubectl get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded
kubectl get --raw='/readyz?verbose'

# Inventory controller images so you can check compatibility
kubectl get deploy,ds,sts -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{.spec.template.spec.containers[*].image}{"\n"}{end}'

Find deprecated and removed APIs

Kubernetes deprecates API versions well ahead of removing them, but when removal happens, any manifest, Helm chart or controller still using the old version will fail to apply. This is the single most common cause of broken deployments after an upgrade.

Attack it from three directions:

  • Scan your source. Open-source scanners such as pluto and kubent (kube-no-trouble) inspect manifests, Helm releases and live clusters for API versions that are deprecated or removed in a target release. Run them in CI against your Git repositories so new problems never merge.
  • Ask the API server. The API server records requests to deprecated APIs in a metric and adds a warning header to responses. This catches clients that never appear in your repositories, such as old operators or scripts.
  • Check provider insights. Some managed services surface upgrade readiness findings, including deprecated API usage, in their console or API. Use them as a second opinion.
# Which deprecated APIs have clients requested recently?
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis

# Example output line (fields tell you group, version, resource and removal release):
# apiserver_requested_deprecated_apis{group="policy",removed_release="1.25",resource="podsecuritypolicies",subresource="",version="v1beta1"} 1

Once you find an offender, update the manifest to the replacement API version, update the Helm chart, or upgrade the controller. Remember that objects already stored in etcd are converted by the API server; the risk is in clients that create or update resources using the old version.

Protect workloads with PodDisruptionBudgets

Node upgrades work by cordoning and draining nodes. Draining uses the Eviction API, which respects PodDisruptionBudgets (PDBs). A PDB tells Kubernetes how many replicas of an application may be unavailable at once due to voluntary disruption.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: checkout-pdb
  namespace: shop
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: checkout

A PDB only helps if the workload is actually resilient. Pair it with:

  • At least two replicas, spread across nodes and zones with topologySpreadConstraints or pod anti-affinity.
  • Accurate readiness probes, so traffic only reaches pods that can serve it.
  • Graceful shutdown: handle SIGTERM, finish in-flight requests, and set terminationGracePeriodSeconds to match.
Watch for PDBs that block drains forever. A PDB with maxUnavailable: 0, or minAvailable equal to the replica count, means no pod can ever be evicted. Drains will stall, and some managed services will eventually force the eviction after a timeout. Audit PDBs before the window. 
# Find PDBs that currently allow zero disruptions
kubectl get pdb -A
# Look for ALLOWED DISRUPTIONS = 0 on workloads that are otherwise healthy

Upgrade the control plane

On a managed service this is a single API call or console action; on a self-managed cluster it is the kubeadm upgrade sequence on each control plane node. In both cases:

  • Upgrade a non-production cluster first and let it soak for long enough to exercise your normal deployment and batch cycles.
  • Watch API server error rates and latency during and after the change.
  • Confirm that controllers reconcile normally, admission webhooks respond, and CI pipelines can still deploy.

Admission webhooks deserve special attention. If a webhook's backing service is unavailable and its failure policy is Fail, the API server will reject matching requests, which can stall the rest of the upgrade.

Upgrade nodes: surge or blue/green

There are two common strategies for nodes. Both avoid downtime when workloads are configured correctly.

In-place surge upgrades

The node pool creates extra nodes on the new version (the surge), then cordons and drains old nodes one batch at a time. Surge is controlled by settings such as maximum surge and maximum unavailable. Higher surge is faster but needs more spare capacity.

# GKE: add one surge node at a time and never take nodes away before replacements are ready
gcloud container node-pools update default-pool \
  --cluster=prod-cluster --region=europe-west1 \
  --max-surge-upgrade=1 --max-unavailable-upgrade=0

# AKS: allow a percentage of extra nodes during upgrade
az aks nodepool update \
  --resource-group prod-rg --cluster-name prod-cluster \
  --name userpool --max-surge 33%

Blue/green node pools

Create a brand-new node pool on the target version, cordon the old pool, drain it gradually, and delete it once you are satisfied. This takes more capacity but gives you the cleanest rollback: if something is wrong, uncordon the old pool and drain the new one.

# Move workloads from an old node pool to a new one, one node at a time
for node in $(kubectl get nodes -l pool=blue -o name); do
  kubectl cordon "$node"
done

for node in $(kubectl get nodes -l pool=blue -o name); do
  kubectl drain "$node" --ignore-daemonsets --delete-emptydir-data --timeout=10m
  sleep 60   # give rescheduled pods time to become Ready
done

The pool label above is an example; use whatever label your provider or node pool configuration applies. Note that --delete-emptydir-data discards data in emptyDir volumes, which is normally scratch space, but confirm that nothing depends on it.

Validate after the upgrade

Do not declare victory when the progress bar finishes. Run a short validation script and keep watching for a day:

  • All nodes report the expected kubelet version and are Ready.
  • Every Deployment, StatefulSet and DaemonSet has its desired number of ready replicas.
  • Synthetic checks against public endpoints pass; error rates and latency are at baseline.
  • A test deployment through your normal pipeline succeeds, proving CI, admission and GitOps still work.
# Kubelet version per node
kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion

# Deployments whose ready count does not match the desired count
kubectl get deploy -A --no-headers | awk '{split($3, r, "/"); if (r[1] != r[2]) print}'

Plan the rollback before you need it

Be honest about what can and cannot be rolled back:

  • Control planes generally cannot be downgraded on managed services, and downgrading a self-managed control plane is risky because stored objects may already be written in newer formats. Your safety net for the control plane is testing in lower environments and, in the worst case, restoring into a fresh cluster at the old version.
  • Nodes can be rolled back by keeping the old node pool around (blue/green) until the new one is proven.
  • Workloads can be rolled back through your GitOps or deployment tooling, provided manifests use API versions both releases understand.

For critical platforms, some teams go further and upgrade by building a new cluster at the target version and shifting traffic to it with DNS or a global load balancer. It costs more but makes rollback a traffic change rather than an infrastructure change. Our GitOps guide explains how to make a new cluster reproducible enough for this to be practical.

Key takeaways

  • Upgrade one minor version at a time, control plane first, and read the release notes for every version you pass through.
  • Scan manifests, Helm releases and live API traffic for deprecated APIs well before the window, and block new ones in CI.
  • Give every important workload multiple replicas, topology spread, good probes, graceful shutdown and a sensible PDB.
  • Use surge upgrades for routine changes and blue/green node pools when you want the cleanest node rollback.
  • Validate with real deployments and synthetic checks, not just node status.
  • Accept that control planes rarely roll back, and test accordingly in lower environments.
