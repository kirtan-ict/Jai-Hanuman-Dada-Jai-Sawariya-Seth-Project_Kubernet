Versions

Kubernetes version lifecycle and upgrades

The Kubernetes project ships a new minor release (1.x) roughly three times a year. Each minor release receives patch releases for about 14 months: roughly a year of standard support plus a short overlap period to upgrade. In practice that means a cluster left alone falls out of support in a little over a year, and upgrading becomes a routine, several-times-a-year task rather than a project.

Check current versions at the source. Supported releases and end-of-life dates change with every release. Always confirm them on the official kubernetes.io/releases page and in your cloud provider's or vendor's own version calendar, which may differ from upstream and may offer paid extended support.

Upgrade guidance

  • One minor version at a time for the control plane. You cannot skip minor versions.
  • Respect version skew: nodes may lag the control plane by a limited number of minor versions, but never run ahead of it. Check the skew policy for your version.
  • Find deprecated APIs first using the API server's deprecated-API metrics or tools such as Pluto or kube-no-trouble, and fix manifests and Helm charts before upgrading.
  • Upgrade add-ons deliberately: CNI, CSI drivers, ingress controllers, cert-manager and operators each have their own compatibility matrix.
  • Back up before you start: an etcd snapshot (self-managed) and Velero backups of critical namespaces.
  • Rehearse in a lower environment on the same version path, then upgrade production with surge capacity and PodDisruptionBudgets in place.
  • Plan a regular cadence, for example one minor upgrade per quarter, so you never fall more than one or two versions behind.
Checklist

Production-readiness checklist

Expand each area. If you cannot tick most items, the cluster is a pilot, not production. Our free assessment walks through a shorter version of this list.

Cluster and control plane
  • Highly available control plane (managed, or three members across failure domains).
  • Kubernetes version within the supported window, with an upgrade plan.
  • Separate node pools for system components and workloads.
  • Cluster built entirely from code (Terraform, Cluster API or equivalent).
  • Certificate expiry monitored, with rotation automated or scheduled.
Security and access
  • SSO for humans, short-lived credentials, no shared admin kubeconfig.
  • RBAC with least privilege; cluster-admin limited to break-glass accounts.
  • Pod Security Standards (baseline or restricted) enforced per namespace.
  • Admission policy (Kyverno or Gatekeeper) for image sources, labels and resource limits.
  • Secrets encrypted at rest and sourced from a secrets manager.
  • Image scanning in CI and, ideally, signature verification at admission.
  • API server not openly exposed to the internet; audit logging enabled.
Networking
  • IP ranges planned for growth and not overlapping other networks.
  • Default-deny NetworkPolicies with explicit allows between services.
  • Ingress or Gateway API with TLS everywhere and automated certificates.
  • DNS (CoreDNS) scaled and monitored; NodeLocal DNSCache where load is high.
Workloads
  • CPU and memory requests on every container; memory limits set.
  • Liveness, readiness and, where slow to start, startup probes.
  • At least two replicas for stateless services, spread across zones or nodes.
  • PodDisruptionBudgets so upgrades and drains do not take services down.
  • Graceful shutdown handling (preStop hooks, termination grace periods).
Observability
  • Metrics for cluster, nodes and applications with retention that fits your needs.
  • Centralised logs that survive pod and node loss.
  • Alerts on symptoms users feel, routed to an on-call rotation with runbooks.
  • Tracing for request paths that cross several services.
Backup and disaster recovery
  • etcd snapshots (self-managed) stored off-cluster.
  • Velero or equivalent backups of resources and persistent volumes.
  • Documented recovery point and recovery time objectives.
  • A restore drill performed in the last quarter.
Delivery and change
  • All changes delivered through CI/CD or GitOps, not manual kubectl apply.
  • Environments promoted through the same pipeline.
  • Rollback path tested for applications and platform components.
Cost
  • Cost visibility per namespace or team (for example with OpenCost).
  • Autoscaling for pods and nodes; idle environments scaled down.
  • Requests reviewed regularly against actual usage.
Day-2 operations

Runbook outlines

Short outlines of common recovery procedures. They assume a self-managed cluster where noted; managed services handle some steps for you. Replace values in angle brackets, and adapt paths to your distribution.

1. Node failure

Symptoms: node NotReady, pods stuck Terminating or Unknown. Goal: move workloads safely, then repair or replace the node.

# Identify the node and what runs on it
kubectl get nodes -o wide
kubectl describe node <node>
kubectl get pods -A -o wide --field-selector spec.nodeName=<node>

# Stop new scheduling, then evict workloads (respects PodDisruptionBudgets)
kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=10m

# After repair: allow scheduling again
kubectl uncordon <node>

# If the machine is gone for good, remove the Node object
kubectl delete node <node>

Check whether stateful pods with attached volumes need the old volume attachment released before they can start elsewhere. With autoscaled node groups, replacing the instance is often faster than repairing it.

2. etcd snapshot and restore (self-managed)

Use when the cluster state is corrupted or lost. Restoring etcd rolls the whole cluster back to the snapshot time, so treat it as a last resort and stop all API servers first.

# Take a snapshot (kubeadm-style stacked etcd paths)
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /var/backups/etcd-snapshot.db

# Verify the snapshot
etcdutl snapshot status /var/backups/etcd-snapshot.db -w table

# Restore on a control-plane node: stop static pods, restore to a new data dir
mkdir -p /root/manifests-backup
mv /etc/kubernetes/manifests/*.yaml /root/manifests-backup/
etcdutl snapshot restore /var/backups/etcd-snapshot.db --data-dir /var/lib/etcd-restored
# Point the etcd static pod's hostPath at /var/lib/etcd-restored, then:
mv /root/manifests-backup/*.yaml /etc/kubernetes/manifests/
kubectl get nodes
kubectl get pods -n kube-system

Multi-member clusters must be restored on every member with matching cluster settings. Distributions have their own helpers, for example RKE2's --cluster-reset with a restore path. Follow your distribution's documented procedure.

3. Certificate expiry

Symptoms: x509: certificate has expired errors, kubectl and kubelets unable to reach the API. kubeadm-issued certificates last one year by default and are renewed during control-plane upgrades, so clusters that have not been upgraded in a year are at risk.

# Check expiry dates (kubeadm clusters)
kubeadm certs check-expiration

# Renew all control-plane certificates on each control-plane node
kubeadm certs renew all
# Then restart the control-plane static pods (API server, controller manager,
# scheduler, etcd), e.g. by moving their manifests out and back in

# Refresh your admin kubeconfig
cp /etc/kubernetes/admin.conf $HOME/.kube/config

# Check a kubelet client certificate
openssl x509 -noout -enddate -in /var/lib/kubelet/pki/kubelet-client-current.pem

# For cert-manager-issued certificates
kubectl get certificates -A
kubectl describe certificate <name> -n <namespace>

4. Failed upgrade rollback

Kubernetes does not support downgrading the control plane in place. Your safety net is the backup taken before the upgrade, plus the ability to fix forward. For node pools and applications, rolling back is usually straightforward.

# Assess: versions, API health and system pods
kubectl version
kubectl get nodes
kubectl get --raw='/readyz?verbose'
kubectl get pods -n kube-system

# kubeadm: re-check the plan; a failed 'kubeadm upgrade apply' rolls back
# automatically and keeps backups under /etc/kubernetes/tmp
kubeadm upgrade plan

# Find workloads broken by removed APIs
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis

# Roll back an application rollout
kubectl rollout history deployment/<name> -n <namespace>
kubectl rollout undo deployment/<name> -n <namespace>

On managed services, a failed node-pool upgrade is typically handled by creating a fresh node pool on the previous supported version and draining the new one. If the control plane itself is unhealthy after upgrade, open a provider support case immediately. For self-managed clusters, restoring the pre-upgrade etcd snapshot onto the previous binaries is the last-resort rollback.

5. CrashLoopBackOff triage

The container starts, exits and is restarted with increasing back-off. The cause is almost always in the previous container's logs, its exit code or its configuration.

# What is failing, and how often
kubectl get pods -n <namespace>
kubectl describe pod <pod> -n <namespace>

# Logs from the crashed (previous) container
kubectl logs <pod> -n <namespace> --previous
kubectl logs <pod> -n <namespace> -c <container> --previous

# Exit code and reason (137 often means OOMKilled)
kubectl get pod <pod> -n <namespace> \
  -o jsonpath='{.status.containerStatuses[*].lastState.terminated}'

# Recent events in the namespace
kubectl get events -n <namespace> --sort-by=.lastTimestamp

# Debug with an ephemeral container sharing the process namespace
kubectl debug -it <pod> -n <namespace> --image=busybox:1.36 --target=<container>

# If a recent change caused it, roll back
kubectl rollout undo deployment/<name> -n <namespace>

Common causes: missing ConfigMap or Secret keys, wrong command or arguments, failing liveness probes on slow starts, out-of-memory kills, and dependencies (databases, DNS) not reachable at start-up.

Honest advice

When NOT to use Kubernetes

We build Kubernetes platforms for a living, and we still recommend against them fairly often. Kubernetes pays off when you have many services, many teams or demanding operational requirements. Below that line, its complexity can cost more than it saves.

Consider something simpler if…

  • You run a handful of services that a PaaS, serverless platform or managed container service (such as Cloud Run, Azure Container Apps or ECS) can host.
  • Nobody on the team will own the cluster, and you do not plan to buy support.
  • The application is a monolith with steady traffic that runs well on a couple of VMs.
  • Your main problem is application architecture or delivery process; Kubernetes will not fix that.

Kubernetes usually earns its keep when…

  • Many services and teams need a common, self-service deployment platform.
  • You need portability across clouds, data centres or edge sites.
  • Workloads need autoscaling, self-healing and frequent, safe releases.
  • You run specialised workloads such as GPUs, batch jobs or stateful operators at scale.

Unsure which side you are on? The decision guide and a readiness assessment will tell you, and we will say so if the answer is "not yet".

Glossary

TermMeaning
Control planeThe components that run the cluster: API server, scheduler, controller manager and etcd.
etcdThe consistent key-value store holding all cluster state. Losing it without a backup means losing the cluster's configuration.
NodeA machine (VM or server) that runs pods via the kubelet and a container runtime.
PodThe smallest deployable unit: one or more containers sharing network and storage.
Deployment / StatefulSet / DaemonSetControllers for stateless replicas, stateful replicas with stable identity, and one pod per node respectively.
ServiceA stable virtual IP and DNS name that load-balances to a set of pods.
Ingress / Gateway APIAPIs for routing external HTTP(S) traffic into services. Gateway API is the newer, more expressive successor.
CNIContainer Network Interface: the plugin providing pod networking, such as Cilium or Calico.
CSIContainer Storage Interface: the plugin standard for attaching persistent storage.
CRD and OperatorCustom Resource Definitions extend the API; operators are controllers that manage software using them.
HPAHorizontal Pod Autoscaler: adds or removes pod replicas based on metrics.
Cluster Autoscaler / KarpenterTools that add and remove nodes based on pending pods and utilisation.
PodDisruptionBudgetA limit on how many pods of an app may be voluntarily disrupted at once, protecting availability during drains and upgrades.
Taints and tolerationsA way to keep pods off certain nodes unless they explicitly tolerate them, for example GPU nodes.
RBACRole-Based Access Control: who can do what to which resources.
GitOpsManaging cluster state declaratively from Git, with an agent (Argo CD, Flux) reconciling changes.
HelmA package manager for Kubernetes applications, using templated charts.
Service meshA layer (such as Istio or Linkerd) adding mTLS, traffic control and telemetry between services.
Day-2 operationsEverything after the initial build: upgrades, patching, monitoring, backups, scaling and incident response.
