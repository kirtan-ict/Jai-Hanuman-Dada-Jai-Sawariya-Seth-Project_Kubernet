On-premises Kubernetes

Kubernetes in your own data centre

Run clusters on the virtualisation platform you already own. We take care of the parts a cloud would normally hide from you: highly available control planes, load balancers, persistent storage and etcd backups.

When this fits

  • You have virtualisation capacity and hardware that is not yet at end of life.
  • Data residency, latency to existing systems, or contracts keep workloads in your facility.
  • Workloads are steady enough that owned capacity beats pay-as-you-go pricing.
  • You have, or want to build, an infrastructure team that is comfortable owning the stack.
  • You are modernising VM-based apps and want a gradual path to containers.

When it doesn't

  • Demand is spiky and you would be buying hardware for a peak you rarely hit.
  • Nobody on the team can own storage, networking and upgrades long-term (consider managed cloud or our support plans).
  • The hypervisor licence is about to change significantly; it may be worth evaluating bare metal first.
  • You need a vendor-supported distribution for compliance; look at enterprise platforms.
Reference architecture

Cloud-like building blocks, on your hardware

In the cloud a LoadBalancer Service or a PersistentVolumeClaim just works. On-premises, each of those needs a deliberate design. We pick components that match your network and storage, then document how each one fails and recovers.

  • Highly available API behind a virtual IP, so a single VM or host failure is a non-event.
  • Anti-affinity rules on the hypervisor so control-plane VMs never share a host.
  • Storage chosen per workload: replicated software-defined storage or your existing SAN through CSI.
  • etcd snapshots taken on a schedule and copied off the cluster, with a tested restore.
Implementation

What we implement

  • Distribution selection and build: upstream kubeadm, RKE2 (security-focused, CIS-friendly defaults) or a vendor platform.
  • VM templates and automated provisioning with Terraform, Ansible or Cluster API providers for vSphere, OpenStack, Nutanix and Proxmox.
  • HA control plane with kube-vip or an external load balancer, stacked or external etcd.
  • MetalLB in L2 or BGP mode for Service load balancers, or integration with your existing F5, Citrix or HAProxy appliances.
  • Persistent storage with Rook-Ceph, Longhorn or vendor CSI drivers (vSphere CSI, Nutanix CSI, NetApp Trident, Pure Portworx).
  • CNI selection and network policy with Cilium or Calico, aligned with your VLANs and firewalls.
  • Integration with corporate DNS, LDAP / Active Directory SSO, proxies and internal certificate authorities.
  • Scheduled etcd snapshots and Velero backups to S3-compatible object storage.

Day-2 operations

Day-2 support we provide

On-premises, you own every layer. Our support plans cover the jobs that are easy to postpone and painful to get wrong.

Upgrades

One minor version at a time, control plane first, then rolling worker replacement from fresh VM templates. Pre-flight checks for deprecated APIs and add-on compatibility before every step.

Patching

OS and kernel patching through image rebuilds or controlled in-place updates with node drains, plus container runtime and CNI patch releases.

Monitoring

etcd health, disk latency and database size, storage pool capacity, certificate expiry, node pressure and hypervisor-level alerts in one view.

Backup and DR

Automated etcd snapshots, Velero backups of namespaces and volumes, and restore drills to a scratch cluster so recovery steps are proven.

Scaling

Capacity forecasting against your hardware, adding workers through templates or Cluster API, and expanding storage pools before they fill.

Incident response

Quorum loss, expired certificates, full disks, storage degradation and network partitions, handled with runbooks we write together with your team.

Lessons learned

Common pitfalls we prevent

  • Expired cluster certificates taking the API down roughly a year after install.
  • etcd on slow shared storage, causing leader elections and API timeouts.
  • All control-plane VMs on one host because anti-affinity was never set.
  • No tested etcd restore, discovered during the incident that needs it.
  • Storage replication on the same failure domain, so one host loss still loses data.
  • Pod and Service CIDRs overlapping corporate ranges and breaking routing.
  • Hand-built "pet" nodes that drift apart and cannot be rebuilt.

FAQ

On-premises questions

Related services: cluster build, reliability engineering, VM-to-container migration, and 24/7 support.

kubeadm or RKE2?
kubeadm gives you upstream Kubernetes with full control and more assembly work. RKE2 packages Kubernetes with hardened defaults, an embedded etcd and a simpler upgrade path. For most enterprise on-premises builds without a vendor subscription, RKE2 saves effort; kubeadm is a good fit when you want strictly upstream components.
Which storage should we use?
If you already have a SAN or HCI platform with a supported CSI driver, using it is often simplest. Rook-Ceph suits larger clusters that want software-defined block, file and object storage. Longhorn is easier to operate for small and mid-sized clusters. Databases with strict latency needs may be better on local disks with application-level replication.
How many control-plane nodes do we need?
Three for production. etcd needs a majority to stay available, so three nodes tolerate one failure. Five tolerate two but add write latency and are rarely needed.
Can we run on the hypervisor we already have?
Usually yes. vSphere, OpenStack, Nutanix and Proxmox all work well; the differences are mainly in automation tooling and CSI drivers.
